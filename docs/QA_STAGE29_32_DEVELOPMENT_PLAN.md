# QA 29~32단계 개발 계획

## 1. 문서 목적

이 문서는 행사 전 추가 QA에서 확인된 정보상점 결제, 게임 초기화, 참가자 자산 관리,
장중 사건 알림, 뉴스 창, 기업 설명, 전체 종목 차트 및 화면 배치 문제를 지석(Backend)과
재헌(Frontend)이 순서대로 개발하기 위한 협업 기준이다.

관련 요구사항을 기능 의존성에 따라 **4단계, PR 4개**로 압축한다. Backend 데이터와 API
계약을 먼저 확정하고 Frontend를 연결한 뒤 마지막 단계에서 전체 회귀 QA를 수행한다.

## 2. QA 요구사항

1. 정보상점 구매 재화를 기존 포인트가 아닌 투자 현금으로 통일한다.
2. 게임 초기화 후에도 관리자가 배정한 월별 사건 일정을 유지한다.
3. 시장정보 단서 관리의 수정 버튼 문구를 정보 제목과 관계없이 `정보 수정`으로 통일한다.
4. 정보 구매 전 배경 블러가 적용된 커스텀 확인 창을 한 번만 표시한다.
5. 뉴스 탭에서 뉴스를 플로팅 뉴스 창으로 열 수 있게 한다.
6. 장중 사건 예고·발생·처리·마감 상태와 남은 시간을 알림과 타이머에 표시한다.
7. 관리자 참가자 화면에서 현금과 보유 종목을 정확히 조회하고 즉시 수정할 수 있게 한다.
8. DB의 장중 사건 제목 접두사를 `[장중]`에서 `[속보]`로 통일한다.
9. 모든 기업 차트를 한 화면에 표시하고 선택한 종목만 강조한다.
10. `실시간 연결됨` 표시를 `INFOSYS INVESTKING` 오른쪽으로 옮긴다.
11. 기업 설명 창의 크기를 제한하고 긴 설명을 자동으로 줄바꿈한다.
12. 대기 안내를 오른쪽 아래 알림으로 옮기고 시장·주문보유 화면의 기존 안내 영역을 제거한다.

## 4. 29단계 — 데이터·API 정상화

**구현 상태: 완료.** 현금 구매 계약은 기존 구현을 재검증했고, 초기화·참가자 자산·사건 시간 계약과 회귀 테스트를 보완했다.

### 4.1 정보상점 현금 결제

- 신규 정보 구매에서 `user_reward_wallets.points`를 사용하지 않는다.
- 참가자의 투자 지갑인 `wallets.cash`를 구매 재화로 사용한다.
- `GET /api/intelligence/me`는 현재 현금, 판매 정보, 구매 기록을 반환한다.
- 신규 구매 응답과 구매 기록은 `cash`, `paidCash` 계약을 사용한다.
- 과거 `paid_points` 구매 기록은 조회 호환성을 위해 보존하되 신규 구매에는 사용하지 않는다.
- 다음 절차를 하나의 DB Transaction으로 처리한다.
  1. 게임, 참가자, 지갑과 정보 행 잠금
  2. 게임 상태·공개 월·최신 가격·잔액 재검증
  3. 현금 차감
  4. 구매 스냅샷 저장
  5. 변경된 현금과 구매 결과 반환
- 같은 정보의 중복 구매와 잔액을 초과한 동시 구매를 차단한다.
- 응답 유실 시 자동 재구매하지 않고 최신 구매 내역으로 결과를 복구한다.

### 4.2 게임 초기화 후 사건 배정 유지

현재 초기화 로직은 `game_events`와 `event_schedule_states`를 삭제한다. 이를 다음 방식으로
변경한다.

- 관리자가 배정한 `game_events` 행과 `event_schedule_states.mode=MANUAL`을 유지한다.
- 각 배정의 실행 상태만 초기화한다.
  - `scheduled_at = NULL`
  - `warning_sent_at = NULL`
  - `applied_at = NULL`
- 이전 게임의 `stock_price_changes`와 `stock_price_history`는 삭제한다.
- 기업의 `current_price`를 `initial_price`로 되돌린다.
- 참가자, 세션, 지갑, 보유 종목, 주문, 구매 기록과 순위는 기존 초기화 정책대로 정리한다.
- 초기화 직후 관리자 일정 조회에서 1~12월, 장중 18개, 마감 12개가 그대로 보여야 한다.
- 새 게임 시작 시 현재 월의 `scheduled_at`을 새로운 `roundStartedAt` 기준으로 다시 계산한다.

### 4.3 참가자 자산 API

관리자 참가자 조회는 각 참가자에 다음 값을 명시적으로 반환한다.

| 필드 | 내용 |
|---|---|
| `userId` | 참가자 식별자 |
| `nickname` | 참가자 이름 |
| `cash` | 현재 투자 현금 |
| `stockValue` | 현재 주가 기준 주식 평가액 |
| `totalAssets` | 현금과 주식 평가액 합계 |
| `holdings[]` | 기업 코드·이름·보유 수량·현재가·평가액 |
| `connected` | 현재 Socket 연결 여부 |

- PostgreSQL `BIGINT` 문자열을 JSON 숫자로 명시적으로 변환한다.
- 지갑이나 보유 종목이 없는 참가자와 실제 0원을 구분한다.
- 비활성 기업의 기존 보유 수량도 관리자에게 표시한다.
- 관리자 인증이 없으면 참가자 자산을 반환하지 않는다.

### 4.4 자산 수정 API

- 수정은 `WAITING` 또는 `PAUSED` 상태에서만 허용한다.
- 현금과 여러 종목 수량을 하나의 Transaction으로 수정한다.
- 참가자·지갑·보유 종목을 잠그고 수정 전 값이 최신 DB 값과 같은지 검증한다.
- 다른 관리 작업이 먼저 반영됐다면 `409 ASSET_CONFLICT`로 거부하고 `current`에 최신 값을 반환한다.
- 음수, 소수, 안전 정수 범위를 벗어난 값과 존재하지 않는 기업을 거부한다.
- 수정 전후 값, 관리자 작업 시각과 요청 ID를 감사 기록에 남긴다.

### 4.5 사건 제목과 시간 계약

- DB의 장중 사건 제목에서 `[장중]` 접두사를 `[속보]`로 변경한다.
- 이후 새 장중 사건 생성 시에도 `[속보]` 표기를 사용한다.
- 장중 사건 응답에 다음 값을 제공한다.
  - `scheduledAt`
  - `warningSentAt`
  - `appliedAt`
  - `triggerOffsetSeconds`
  - `preannounceSeconds`
  - 거래 정지 및 재개 여부
- 게임 시작 전에는 절대 시각 대신 거래 시작 기준 offset을 사용한다.
- 서버 재시작 후에도 저장된 `scheduledAt`과 `appliedAt`으로 상태를 복구한다.

### 4.6 Backend 테스트

- 포인트가 0이어도 현금이 충분하면 정보 구매 성공
- 현금 부족 시 구매와 차감 모두 실패
- 동시 구매 시 잔액 초과 방지
- 초기화 전후 월별 사건 ID·월·순서·종류 유지
- 초기화 후 사건 실행 시각과 적용 상태만 제거
- 두 번째 게임에서 같은 사건이 정확히 한 번 다시 적용
- 참가자 현금·보유 종목·평가액·총자산 계산 검증
- 자산 동시 수정과 오래된 수정 요청 거부
- `[장중]` 제목이 관리자·참가자 응답에 남지 않음

## 5. 30단계 — 구매·뉴스·알림 UX

### 5.1 정보 구매 확인 Modal

`정보 구매` 버튼을 누르면 브라우저 기본 확인창이나 카드 아래 인라인 확인 영역 대신 공통
커스텀 Modal을 표시한다.

Modal 표시 정보:

- 정보 제목
- 구매 가격
- 현재 현금
- 구매 후 예상 현금

동작 규칙:

1. Modal 뒤의 화면에 반투명 overlay와 blur를 적용한다.
2. 최초 초점은 `취소` 버튼 또는 제목에 둔다.
3. `취소`와 `구매` 버튼만 표시한다.
4. `구매`를 누르면 추가 확인 없이 API를 한 번 호출한다.
5. 요청 중에는 두 버튼과 기존 구매 버튼을 비활성화한다.
6. 성공하면 Modal을 닫고 현금·상점·보관함을 동시에 갱신한다.
7. 실패하면 Modal 안에 원인을 표시하고 사용자가 직접 다시 시도하게 한다.
8. `Esc`, overlay 클릭, 닫기 동작은 요청 전까지만 허용한다.
9. 구매 결과가 불명확하면 자동 재전송하지 않는다.

### 5.2 뉴스 창으로 보기

- 뉴스 탭 상단에 `뉴스 창으로 보기` 버튼을 추가한다.
- 누르면 기존 플로팅 뉴스 컴포넌트를 연다.
- 뉴스 창은 타이머처럼 이동 및 크기 조절이 가능해야 한다.
- 탭과 플로팅 창은 같은 뉴스 상태를 사용한다.
- 장중 사건 알림에서 뉴스를 열면 해당 기사로 이동하고 제목에 초점을 둔다.
- 같은 기사를 여러 번 열어도 창을 중복 생성하지 않는다.

### 5.3 장중 사건 알림 상태

| 상태 | 표시 예시 | 기준 |
|---|---|---|
| 예고 | `속보 예정 · 00:08 후 발생` | `warningSentAt` 존재, `appliedAt` 없음 |
| 발생 | `속보 발생 · 주가 반영 중` | 예정 시각 도달, 적용 처리 중 |
| 거래 정지 | `사건 처리 중 · 거래 일시정지` | `tradingHalted=true` |
| 종료 | `마감됨 · 거래가 재개되었습니다` | `appliedAt` 존재, 거래 재개 완료 |

- 거래 시작 후 30초 사건은 22초에 예고한다.
- 거래 시작 후 45초 사건은 37초에 예고한다.
- 거래 시작 후 65초 사건은 57초에 예고한다.
- 알림에는 공개 가능한 제목과 상태만 표시한다.
- 사건 발생 전 기사 본문·결과·변동률을 노출하지 않는다.
- 서버 시각과 클라이언트 수신 시각 차이를 보정해 카운트다운한다.
- 새로고침 또는 재접속 시 과거 사건을 새 알림처럼 반복 재생하지 않는다.
- 사건 종료 알림은 자동으로 사라져도 뉴스 기록에는 계속 남는다.

### 5.4 대기·연결 상태 배치

- `대기 중 · 게임 시작을 기다리고 있습니다` 안내를 오른쪽 아래 커스텀 알림으로 이동한다.
- 시장과 주문·보유 화면에서 공간을 차지하던 기존 대기 안내 영역을 제거한다.
- 모바일 하단 네비게이션과 겹치지 않도록 safe area를 적용한다.
- 게임 시작 시 대기 알림을 자동으로 닫는다.
- `실시간 연결됨`을 상단 브랜드 `INFOSYS INVESTKING` 오른쪽에 배치한다.
- 정상 연결은 짧게 표시하고, 끊김·재연결 중·실패 상태에는 원인과 재시도 버튼을 제공한다.

### 5.5 Frontend 테스트

- 구매 확인창이 한 번만 표시되고 API도 한 번만 호출됨
- 배경 blur, 포커스 잠금, `Esc`, 취소 및 구매 동작
- 성공 후 현금·상점·보관함 동시 갱신
- 뉴스 탭과 플로팅 뉴스 창 상태 동기화
- 30·45·65초 사건 카운트다운과 마감 상태
- 재접속 시 오래된 속보 중복 표시 방지
- 대기 알림이 시장·주문 영역 높이에 영향을 주지 않음
- 연결 표시가 데스크톱·모바일 브랜드 영역에서 잘리지 않음

## 6. 31단계 — 관리자·시장 UI

### 6.1 참가자 자산 표

관리자 참가자 화면의 기본 표는 다음 구조로 표시한다.

| 참가자 | 접속 | 현금 | 주식 평가액 | 총자산 | 보유 종목 | 관리 |
|---|---|---:|---:|---:|---|---|
| 홍길동 | 접속 중 | 800,000원 | 350,000원 | 1,150,000원 | 3개 | 자산 수정 |

- 참가자 행을 펼치면 기업별 보유 내용을 하위 표로 표시한다.

| 기업 | 수량 | 현재가 | 평가액 |
|---|---:|---:|---:|
| 한양양조 | 10주 | 11,800원 | 118,000원 |

- 0원과 조회 실패를 다른 UI로 표시한다.
- 보유 종목이 없으면 `보유 종목 없음`을 표시한다.
- 긴 이름은 줄바꿈하되 숫자 열 정렬은 유지한다.
- 모바일에서는 핵심 자산 요약과 펼침 상세 구조로 전환한다.

### 6.2 참가자 자산 즉시 수정

- 각 참가자 행에 `자산 수정` 버튼을 제공한다.
- 커스텀 Modal 또는 Drawer에서 현금과 기업별 수량을 수정한다.
- 현재 서버 값을 초기값으로 표시한다.
- 변경된 필드와 수정 후 총자산 예상값을 강조한다.
- 저장 성공 후 참가자 표와 관리자 순위를 즉시 갱신한다.
- `ASSET_CONFLICT` 발생 시 서버 최신 값을 표시하고 덮어쓰지 않는다.
- 실행 중인 주문 또는 게임 상태 때문에 수정할 수 없으면 이유를 표시한다.

### 6.3 시장정보 단서 관리 문구

- 화면상 수정 버튼 문구는 모든 카드에서 `정보 수정`으로 통일한다.
- `지난해 폭염 기간 대학생 실내 소비 분석서 수정`처럼 제목을 버튼 본문에 붙이지 않는다.
- 접근성을 위해 `aria-label="지난해 폭염 기간 대학생 실내 소비 분석서 정보 수정"`처럼
  실제 정보 제목은 보조 이름에 유지한다.
- 삭제 버튼도 화면상 `정보 삭제`, 보조 이름에는 실제 제목을 포함한다.

### 6.4 기업 설명 창

- 설명 창에 고정 기본 너비와 최대 너비를 적용한다.
- 본문은 `white-space: normal`, `overflow-wrap: anywhere`로 자동 줄바꿈한다.
- 최대 높이를 넘으면 창 내부만 스크롤한다.
- 기업명·업종·설명·현재가·월 등락률의 영역을 분리한다.
- 화면 오른쪽과 아래 경계에서 위치를 자동 보정한다.
- 모바일에서는 종목 행 아래 또는 화면 너비에 맞춘 bottom sheet 형태로 전환한다.
- `×`, `Esc`, 외부 클릭으로 닫고 초점을 원래 기업 이름 버튼으로 돌려보낸다.

### 6.5 Frontend 테스트

- 참가자 자산 숫자와 보유 종목 렌더링
- 0원, 빈 보유 종목, 비활성 기업, 조회 실패 표시
- 자산 수정 성공·검증 실패·동시 수정 충돌
- 정보 수정·삭제 버튼 문구와 접근 가능한 이름
- 긴 기업 설명 줄바꿈과 내부 스크롤
- 작은 모바일 화면에서 설명 창이 화면 밖으로 벗어나지 않음

## 7. 32단계 — 전체 종목 차트·통합 QA

### 7.1 다중 종목 차트

- 차트 화면에 활성 기업의 월별 가격선을 모두 동시에 표시한다.
- 기업 코드별 고정 색상을 사용해 새로고침 후에도 색이 바뀌지 않게 한다.
- 차트 상단에 색상 표시와 기업 이름으로 구성된 범례를 둔다.
- 기본 상태에서는 모든 선의 불투명도를 낮춘다.
- 기업 또는 범례를 선택하면 해당 기업의 선·점·라벨만 뚜렷하게 표시한다.
- 선택하지 않은 기업은 흐리게 유지하되 완전히 숨기지 않는다.
- 선택한 기업을 다시 누르면 전체 비교 상태로 돌아간다.
- 사건 발생 지점은 관련 기업의 선 위에 마커로 표시한다.
- 색상만으로 기업을 구분하지 않도록 범례, 이름, 선 패턴과 선택 상태를 함께 제공한다.
- 모바일 범례는 여러 줄 또는 가로 스크롤로 표시한다.
