# 5단계 Frontend + 기기 간 주문 복구

## 기반 상태

2026-09-16 `origin/main` 8d50154에서 시작. PR #10(4단계 UI), #11(사건 Backend), #12(순위 Backend)가 모두 병합되어 있었다. 이 변경은 기존 사건 Backend에 화면을 연결하고, 사용자 승인에 따라 주문 복구 및 자산·등락률 API를 보완한다. 6단계 순위 UI는 포함하지 않는다.

## 관리자

- 기존 관리자 비밀번호 입력을 사건 API에도 사용하며 메모리에서만 유지한다.
- 사건 목록 조회, 제목·사전 뉴스·결과·기업별 변동률 입력, 생성·수정·삭제 확인, 월별 배정표 조회.
- 제목 100자, 뉴스/결과 각 2000자, 기업 중복 금지, 변동률 -99~1000 정수 검증.
- 사건 수와 전체 개월 수 표시. 사건 부족으로 시작이 거절되면 원인을 안내한다.
- 게임 시작 뒤 수정·삭제·등록 차단. 서버에서도 기존 권한·상태 검사를 수행한다.
- 쓰기 응답이 불확실하면 목록 재조회 전까지 추가 쓰기를 잠근다. 자동 재전송하지 않는다.

## 참가자

- 현재 월 뉴스 조회. 서버의 applied=true 결과만 공개한다. 미리 받은 필드가 있어도 미적용 결과는 렌더링하지 않는다.
- 사건 결과, 기업별 변경 전후 가격, 사건 변동률 표시. 시장 목록은 **초기 주가 대비 누적 등락률**로 명확히 구분한다.
- game/news/event/stock Socket 알림과 5초 HTTP 조회로 뉴스·게임·시장·계좌 복구. 이전 월 뉴스는 새 월 화면에서 숨긴다.
- 서버에서 계산한 cash/stockValue/totalAssets를 사용한다. 순위 확정 UI는 별도 6단계이다.

## 서버에 보관하는 주문

마이그레이션에 `order_intents` 테이블 추가. **배포 전 server에서 npm run db:migrate 실행이 필요하다.** 기존 테이블/데이터를 삭제하지 않는다.

1. Frontend가 UUID 주문 번호를 만들고 가능한 경우 sessionStorage에 보조 기록한다.
2. `/orders/prepare` 성공을 확인한 뒤 `/orders`로 체결을 요청한다. 준비 단계는 금액 예약이나 가격 보장이 아니다.
3. 다른 기기에서 동일 닉네임+PIN으로 복구하면 `/orders/recovery`로 미확인 주문과 최근 체결 20건을 읽는다. localStorage/userId 값만으로 다른 계정에 접근할 수 없다.
4. 한 사용자당 미확인 주문 하나만 허용한다. 사용자 잠금 → 주문 번호 잠금 순서로 준비/체결/취소를 직렬화한다.
5. 기존 번호로 재확인하면 이미 체결된 결과를 반환한다. 미체결이면 **현재 가격**으로 체결될 수 있음을 UI에 알린다.
6. 취소는 체결 전 주문만 취소한다. 이미 체결됐다면 기존 결과를 반환한다. CANCELLED 기록을 남겨 늦게 도착한 준비/체결 요청도 차단한다.
7. 네트워크·인증 만료·서버 오류에서도 기록을 유지한다. PIN 복구 후 계속 확인하거나 취소할 수 있다.

기기가 서버에 준비 요청을 전달하기 전에 꺼졌다면 서버에는 주문이 없으며 체결도 요청하지 않는다. 서버에 도착한 준비 요청은 DB에 남아 다른 기기에서 복구된다. 과거 탭의 sessionStorage 기록은 이전 버전 주문 재확인용 보조 수단으로 유지한다.

## 테스트와 실제 관찰

최종 결과: Frontend 17개 통과, 실제 PostgreSQL 서버 16개 통과(skip 0개), production build 성공.

- Frontend 테스트: 입력 범위/중복 기업, 뉴스 초기 로딩, 결과 비공개, 문자열 escaping, 주문 준비/취소 응답 검증 포함.
- 실제 PostgreSQL 테스트: 신규/복구 쿠키 세션, 기기 변경을 모사한 별도 세션, 미확인 주문 조회, 다른 주문 차단, 동시 같은 번호 체결, 취소/체결 경쟁, 취소 후 늦은 요청, 다른 사용자 접근 차단, 초기 대비 등락률.
- 브라우저: 사건 부족 시 시작 거절 → 상승 사건 등록 및 +20에서 +25로 수정 → 하락 사건 -10 등록 → 게임 시작 → 사전 뉴스만 공개 → B 2주 매수 → 마감 시 B 10000→9000, 총자산 1000000→998000 반영 → 다음 월 A 10000→12500 결과 확인 → 종료.
- 별도 로그인 HTTP 세션에서 보관한 A 1주 주문을 브라우저에서 복구하고 취소함.
- 사용자 화면 320/360/390/412/430/768px에서 clientWidth=scrollWidth 확인. 320px 관리자 화면 배치도 육안 확인.
- 개발 전용 `/test/mobile.html`에서 사용자·관리자·참가 화면과 너비를 선택할 수 있다. production build에 포함하지 않는다.

## 아이폰과 삼성 안드로이드

- 브라우저 기반 반응형 UI. 16px 입력 글자와 최소 44px 버튼, 수량/PIN 숫자 키보드 사용. 음수 변동률은 '-' 입력이 가능한 일반 키보드를 사용한다.
- 운영 환경은 Frontend와 `/api`, `/socket.io`를 같은 HTTPS origin으로 제공한다. NODE_ENV=production에서 세션 쿠키는 Secure이다.
- 실제 기기의 Safari, Chrome, Samsung Internet, 가상 키보드, 회전, Wi-Fi 단절/복귀는 **실기기 확인 전**이다. 이 작업에서 수행한 것은 CSS 너비 검사와 데스크톱 브라우저/실제 DB 검증이다.
- 기기 검증 시 동일 배포 URL로 참가→거래→화면 잠금/복귀→PIN 복구→다른 기기 거래 내역/미확인 주문 확인을 수행한다. 테스트 계정과 운영 계정을 구분한다.
