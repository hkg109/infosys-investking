## 4. 정책·해석 기준

### 4.1 지난 정보

- 공개 월이 지났다는 이유만으로 만료시키지 않는다. 먼저 판매된 다음 달 사건 단서를 사용할 수 있어야 한다.
- 연결 사건이 적용됐거나 해당 배정 월이 종료된 경우 지난 정보로 판정한다.
- 연결 사건이 없는 정보는 임의로 지난 정보로 만들지 않는다. 별도 유효 기간이 필요하면 필드와 정책을 정한 후 적용한다.
- 게임 전체 종료 시 지난 정보 표시 정책을 일관되게 적용한다. 참가자의 결제 기록은 보존한다.
- 기존 24개 단서가 실제 사건과 연결되어 있는지 DB를 확인한다. 여러 사건을 설명하는 단서는 유효 범위를 확인하고, 단일 사건 연결만으로 너무 일찍 만료시키지 않는다.

### 4.2 등락률 상한 — 구현 전 기준 명확화

이 계획은 요청의 ‘절댓값’을 **개별 사건의 기업별 changeRate(%) 상한**으로 해석한다.

- 1~6월: `-30 ≤ changeRate ≤ 30`
- 7~12월: `-50 ≤ changeRate ≤ 50`
- ±30% 또는 ±50%를 반드시 사용한다는 뜻은 아니다. 기사와 효과 방향을 유지하면서 범위 안에서 조정한다.
- 여러 사건이 누적되면 월 시가 대비 종가 변동률은 이 상한을 넘을 수 있다. 예: +30% 두 번은 누적 +69%다.
- **월 전체 누적 등락을 ±30%/±50%로 제한하려는 뜻이라면 이 기준은 바뀌어야 한다. 변동률 구현 전에 해당 해석을 확정한다.**
- 월이 없는 사건 원본은 허용 가능한 전체 범위로 저장하되 배정 월에서 더 엄격하게 검사한다. 이미 배정된 사건의 효과를 수정할 때도 검사한다. 일반 사건과 장중 사건 모두 적용한다.

### 4.3 사건 수와 추가 콘텐츠

현재 콘텐츠에는 장중용 18개(기존 장중 12개 + 예비 6개), 정규 마감용 12개가 있다. 이 중 장중용 2개가 현재 마감으로 배치되어 있다.

- 매월 최소 2개를 만족하려면 장중 사건이 최소 24개이므로 **최소 6개 추가**가 필요하다.
- 권장안은 월별 2·3·4개를 섞어 **장중 36개 + 정규 마감 12개**로 운영하는 것이다. 이 경우 **장중 사건 18개를 추가 작성**한다.
- 권장 개수: 1~12월 `2, 3, 2, 4, 3, 4, 2, 3, 4, 2, 3, 4`.
- 이는 계획안이며 DB 미적용 상태다. 새 사건은 해당 월의 계절·행사와 맞게 작성한다.
- 같은 사건을 여러 달에 복제 배정하지 않는다. 사건별 안정적인 ID와 배정 유일성을 유지한다.
- 장중용 사건의 마감 전환은 UI·서버 모두 막는다. 제목의 ‘속보’ 문자열 대신 명시적 종류 필드를 사용하는 방안을 우선 검토한다.
- 사건마다 사전 기사, 결과 기사, 기업별 효과와 근거를 대조한다. 공개 기사에는 정답 회사 목록이나 수치를 넣지 않는다.
- 기사·효과·단서·JSON·읽기용 문서·DB를 같이 갱신한다.

### 4.4 시간 배치

유지할 값: 거래 270초, 결과 30초, 사건별 거래 정지 3초, 뉴스는 해당 사건 반영 30초 전.

예시이며 모든 달에 동일하게 반복하지 않는다:

| 장중 개수 | 뉴스 공개(시작 후 초) | 사건 반영(시작 후 초) | 반영 간격 |
|---:|---|---|---|
| 2 | 109, 183 | 139, 213 | 74초 |
| 3 | 62, 127, 201 | 92, 157, 231 | 65초, 74초 |
| 4 | 35, 78, 139, 206 | 65, 108, 169, 236 | 43초, 61초, 67초 |

- 요구 범위는 30~80초지만 30초 예고+3초 정지 구간이 겹치지 않도록 실제 간격은 33초 이상으로 설계한다.
- 마지막 사건 반영+3초 정지가 270초보다 앞에 끝나야 한다. 마지막 반영 후 주문할 시간도 확보한다.
- 최종 시간표는 DB에 고정 저장한다. 일시정지·재개 시 남은 시간이 보존되어야 한다.
- 뉴스 카운트다운의 목표는 해당 사건의 주가 반영 시점이다. 장중 사건을 월 전체 마감까지 기다리는 것으로 표시하지 않는다.

## 5. QA 실행 절차

### 37단계 검증

1. 미구매 목록 응답·구매 확인창에서 숨긴 원제목·본문이 노출되지 않는지 확인한다.
2. 구매 → 전체 정보 확인 → 연결 사건 적용 → 회색 축소 및 열기 차단 → 재접속 유지 순서로 검증한다.
3. 과거 공개 월이지만 아직 발생하지 않은 사건의 단서가 유효한지 확인한다.
4. 지마이너스 컴퍼니 선택 → 주문창 → 확인창 → 실제 주문 요청의 회사 일치, 다른 회사로 전환 후 재진입을 검증한다.
5. 회사 설명, 보유·주문 결과·최근 내역의 이름, 차트 상세 접기와 키보드 조작을 확인한다.

### 38단계 검증

1. 12개월 모두 장중 2~4개인지, 정규 마감 12개가 유지되는지 검사한다.
2. 6월/7월 경계에서 ±30·±50 허용, ±31·±51 거부를 검증한다. 기존 배정 사건 수정과 월 이동도 포함한다.
3. 시간표의 초 정밀도, 30~80초 간격, 예고와 정지 구간 비중첩, 거래 종료 전 처리 조건을 검증한다.
4. 모의 시계로 예고 → 사건 반영 → 3초 정지 → 거래 재개 → 다음 사건 → 월 마감을 실행한다.
5. 동일 사건 중복 반영 방지, 재접속·일시정지·재개·서버 재시작 후 복구를 확인한다.
6. 로컬 DB 백업 후 대기 상태에서 적용하고 기사·효과·배정·단서를 원본 파일과 대조한다.

### 39단계 최종 검증

1. 관리자·참가자·중계 화면에서 한 달 전체 흐름과 12개월 배정 경계를 검증한다.
